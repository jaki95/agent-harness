### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack to review and land.** The sibling of **Autopilot-full**.

Use the host's delegation, Git, authenticated GitHub CLI (`gh`), filesystem, execution, verification, and supported watch or wake tools within task authorization and host permissions. Resolve named skills through Harness's catalog rules. Use configured role models or parent inheritance; prefer independent model families for verification when available and report missing diversity. Report unavailable delegation, controls, access, or unattended execution without claiming those steps completed. PR operations, posts, thread resolutions, merges, and CI retriggers follow task authorization. Follow Harness and the bundled Opening a PR playbook for authorized PR work.

1. **Run the owner loop unchanged.** Use GitHub CLI (`gh`) for all PR create, edit, view, watch, and merge operations. Do not require Origin or Graphite. One host delegate per PR owns its change end to end: build, first push, a ready PR opened before self-proof, self-proof (gates, CI, receipts), skeptical Bugbot triage per `../references/bugbot-triage.md`, a slop-strip (the **deslop** skill), the **no-comments** skill, and babysit to green per `babysit.md`. Owners declare their committed acceptance record before implementation or measurement per Autopilot-full step 2 and `../references/acceptance-record.md`. Owners parallelize when the work is self-contained. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Keep the trail uncommitted and return it in the report. Owners also keep the `children.tsv` of Autopilot-full step 2.
2. **Audit on a real loop.** The root runs an audit tick every hour. On the operator's go, the root arms a supported host watch or wake mechanism with a prompt that runs this tick every hour, per **Autopilot-full** (`autopilot-full.md`) step 6. Never leave the cadence to memory or lossy completion notifications. Disclose missing unattended execution without claiming an hourly audit is armed. At each tick, re-read this playbook from its installed Harness package location and audit the operation against it. Fix drift during that tick. Probe each owner with a generic liveness or status check. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. An exceeded expected runtime without a side effect triggers inspection of host status and the current operation, not an automatic stuck verdict. Replace a confirmed failed or stuck lane promptly, confirming the old writer stopped before reusing its scope or isolating the replacement. Probe all subagents and end the tick per **Autopilot-full** (`autopilot-full.md`) step 6.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's stop, send every owner an immediate zero-writes hold, request supported cancellation or interruption, and report any unconfirmed stop without claiming it stopped.
4. **Verify each round.** Before its code-ready report, the owner runs `acceptance run <manifest.json>` at the clean committed head and includes the head, run ID, and receipt store. The root rechecks that record with `acceptance check <manifest.json>` in the same store before launching the full independent round. Fix rounds append findings, preserve failed repro and investigation history, and cover current-head focused and affected cases per Autopilot-full step 4. A passing preflight never replaces independent review, live proof, or current-head CI. The owner reports its code-ready head SHA once the shipped code is final, and STACK-READY with the exact head SHA when its loop is green. The root verifies each round per **Autopilot-full** (`autopilot-full.md`) step 4, with STACK-READY in place of merge-ready. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** Owners push only their own branches and report the tip, current base, and intended parent. The root is the only topology writer. To append a PR, fetch the intended parent, rebase the child branch onto that exact parent tip, push with `--force-with-lease` only after an `ls-remote` check, and set the PR base to the parent branch. Create it ready with `gh pr create --base <parent-branch>`. Retarget an existing PR with `gh pr edit <pr> --base <parent-branch>`. Only the root PR targets trunk. Never submit or register the chain through `gt`.
7. **Absorb drift at the root, then re-verify what moved.** The root fetches current trunk and rebases the chain from bottom to top. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. A rebase rewrites every SHA above it and voids verdicts at the old SHAs. Apply the patch-id rule in `shipping.md` at each verdict SHA. Anything that is no longer valid goes back through this playbook's step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch-id is unchanged. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up through gh, every link carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it, with their own clicks or by arming merge-when-ready.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
